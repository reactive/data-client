A v0.18 foca em uma modelagem de dados mais rica para valores que variam conforme o contexto da requisição, downloads tipados mais simples e uma correspondência de collections que reflete melhor os filtros reais das APIs.

**Novos recursos:**

- [Schema Scalar](/blog/2026/05/01/v0.18-scalar-typed-downloads#scalar) - Campos de entidade dependentes de lente (por exemplo, valores específicos de um portfólio) sem jamais mutar a entidade subjacente
- [Propriedade `content` do RestEndpoint](/blog/2026/05/01/v0.18-scalar-typed-downloads#content-property) - Downloads de arquivo tipados, respostas em texto e streaming com uma única propriedade
- [`nonFilterArgumentKeys` em resource()](/blog/2026/05/01/v0.18-scalar-typed-downloads#non-filter-argument-keys) - Argumentos de ordenação/paginação não fragmentam suas [Collections](/rest/api/Collection)

**Outras melhorias:**

- [Detecção automática de Content-Type binário](/blog/2026/05/01/v0.18-scalar-typed-downloads#binary-auto-detection) - Imagens, PDFs e outras respostas binárias são tratadas automaticamente, sem nenhuma configuração ([#3868](https://github.com/reactive/data-client/pull/3868))
- [Os tipos de body dos extenders de Collection seguem a semântica dos métodos HTTP](/rest/api/Collection) - Extenders PATCH (`.move`, `.remove`) aceitam bodies parciais; um [RestEndpoint](/rest/api/RestEndpoint) independente deriva um body tipado do schema de entidade da [Collection](/rest/api/Collection) ([#3910](https://github.com/reactive/data-client/pull/3910))
- Exporta [`CollectionOptions`](/rest/api/Collection) de `@data-client/endpoint` e `@data-client/rest` para a construção tipada de [Collections](/rest/api/Collection) ([#3904](https://github.com/reactive/data-client/pull/3904))

## Scalar {#scalar}

[Scalar](/rest/api/Scalar) trata campos de [Entity](/rest/api/Entity) cujos valores dependem de uma "lente" em tempo de execução — como o
portfólio, a moeda ou o locale selecionado. Vários componentes podem renderizar a **mesma** entidade através de
lentes diferentes simultaneamente, cada um vendo os valores corretos, enquanto a entidade em si nunca
muda. Os valores dependentes de lente vivem em uma tabela de células separada e são unidos no momento da desnormalização
a partir dos args do endpoint.

As referências a `name` e `price` permanecem estáveis ao trocar de portfólio porque a entidade `Company`
em si nunca muda — apenas a célula [`Scalar`](/rest/api/Scalar) selecionada pela lente atual. Uma única instância de [`Scalar`](/rest/api/Scalar)
pode servir tanto como campo de [`Entity.schema`](/rest/api/Entity#schema) (entidade pai inferida a partir da visita) quanto
de forma independente dentro de [`Values`](/rest/api/Values), [`[Scalar]`](/rest/api/Array)
ou [`Collection([Scalar])`](/rest/api/Collection) para atualizações baratas somente de colunas (entidade vinculada
explicitamente via [`entity`](/rest/api/Scalar#entity)). Os pks das células são derivados da chave do mapa ou via
[`Scalar.entityPk()`](/rest/api/Scalar#entityPk), que por padrão usa [`Entity.pk()`](/rest/api/Entity#pk), de modo que chaves primárias personalizadas e
compostas funcionam sem precisar sobrescrever nada.

A store normalizada mantém a entidade estável e as células de lente separadas:

```
entities['Company']['1'] = {
  id: '1',
  price: 145.20,
  pct_equity: ['1', 'pct_equity', 'Company'],
  shares: ['1', 'shares', 'Company'],
}

entities['Scalar(portfolio)']['Company|1|A'] = { pct_equity: 0.50, shares: 10000 }
entities['Scalar(portfolio)']['Company|1|B'] = { pct_equity: 0.30, shares: 6000 }
```

A demonstração combina `getCompanies` com uma atualização barata somente de lente, `getPortfolioColumns`, que escreve
na mesma tabela de células — veja a [documentação de Scalar](/rest/api/Scalar) para um passo a passo completo
do comportamento de cache.

[`Scalar`](/rest/api/Scalar) também implementa [queryKey](/rest/api/Scalar#queryKey), então participa diretamente de
[useQuery](/docs/api/useQuery), [Controller.get](/docs/api/Controller#get) e [schema.Query](/rest/api/Query) —
toda a superfície [Queryable](/rest/api/schema#queryable) — enumerando suas células para a lente atual.

[#3887](https://github.com/reactive/data-client/pull/3887) - [Documentação de Scalar](/rest/api/Scalar)

## Propriedade `content` do RestEndpoint {#content-property}

[RestEndpoint](/rest/api/RestEndpoint) agora aceita uma propriedade [`content`](/rest/api/RestEndpoint#content) que controla
como o corpo da resposta é interpretado. O tipo de retorno é inferido automaticamente a partir do valor, e `schema` fica
restrito a `undefined` no nível de tipos para tipos de conteúdo que não sejam JSON.

```typescript
import { RestEndpoint } from '@data-client/rest';

const downloadFile = new RestEndpoint({
  path: '/files/:id/download',
  // highlight-next-line
  content: 'blob',
  dataExpiryLength: 0,
});

// Return type is Blob — inferred from content, no explicit generics needed
const blob: Blob = await ctrl.fetch(downloadFile, { id: '123' });
```

Antes, downloads de arquivo exigiam uma sobrescrita verbosa de `parseResponse`. Agora é uma única propriedade.

| Valor | Interpreta via | Tipo de retorno |
|---|---|---|
| `'json'` | `response.json()` | `any` |
| `'blob'` | `response.blob()` | `Blob` |
| `'text'` | `response.text()` | `string` |
| `'arrayBuffer'` | `response.arrayBuffer()` | `ArrayBuffer` |
| `'stream'` | `response.body` | `ReadableStream<Uint8Array>` |

Definir `content` com um valor que não seja JSON impõe `schema: undefined` no nível de tipos, já que dados binários não podem ser
normalizados. Uma verificação em tempo de execução fornece uma mensagem de erro clara caso um schema normalizável seja usado por acidente.

Funciona com [`extend()`](/rest/api/RestEndpoint#extend) e com [subclasses](/rest/api/RestEndpoint#inheritance):

```typescript
// Extend a JSON endpoint into a blob downloader
const download = jsonEndpoint.extend({
  content: 'blob',
  schema: undefined,
});

// Subclass for a reusable blob endpoint type
class BlobEndpoint<O extends RestGenerics = any> extends RestEndpoint<O> {
  content = 'blob' as const;
}
```

[#3868](https://github.com/reactive/data-client/pull/3868) - [Documentação de `content`](/rest/api/RestEndpoint#content)

## `nonFilterArgumentKeys` em resource() {#non-filter-argument-keys}

[`nonFilterArgumentKeys`](/rest/api/Collection#nonFilterArgumentKeys) permite que [resource()](/rest/api/resource)
declare quais chaves de argumento *não* são usadas para filtrar os resultados da collection — tipicamente opções de ordenação,
paginação ou exibição. Sem isso, cada combinação distinta de args de ordenação ou página criaria um bucket separado de
[Collection](/rest/api/Collection), e itens recém-criados não apareceriam em listas com
args de ordenação diferentes, mesmo que os dados subjacentes devessem corresponder.

```ts
import { Entity, resource } from '@data-client/rest';

class Post extends Entity {
  id = '';
  title = '';
  group = '';
  author = '';
}

const PostResource = resource({
  path: '/:group/posts/:id',
  searchParams: {} as { orderBy?: string; author?: string },
  schema: Post,
  // highlight-next-line
  nonFilterArgumentKeys: ['orderBy'],
});
```

Agora `group` e `author` são chaves de filtro (elas separam [Collections](/rest/api/Collection) em buckets distintos), mas `orderBy` é
compartilhado — `PostResource.getList.push()` adiciona o novo post a *todas* as variantes de `orderBy` de um dado
bucket `{ group, author }`.

Aceita um `string[]`, um `RegExp` ou uma função predicado:

```ts
nonFilterArgumentKeys: /^(orderBy|page|cursor)$/,
```

[#3914](https://github.com/reactive/data-client/pull/3914) - [Documentação de `nonFilterArgumentKeys`](/rest/api/Collection#nonFilterArgumentKeys)

## Detecção automática de Content-Type binário {#binary-auto-detection}

Quando `content` não está definido, [`parseResponse`](/rest/api/RestEndpoint#parseResponse) agora detecta automaticamente Content-Types
binários e retorna `response.blob()` em vez de corromper os dados via `.text()`.

Tipos binários como `image/*`, `audio/*`, `video/*`, `font/*`, `application/octet-stream`, `application/pdf` e
outros agora são tratados automaticamente. Tipos textuais (`text/*`, XML, HTML, JavaScript, CSS etc.) continuam a
usar o fallback de texto existente, com mensagens de erro que levam o schema em conta.

Isso significa que endpoints que servem dados binários com cabeçalhos Content-Type corretos funcionam sem nenhuma configuração:

```typescript
const ep = new RestEndpoint({
  path: '/avatars/:id',
});
// Server responds with Content-Type: image/png
// → automatically returns a Blob (previously corrupted via .text())
```

[#3868](https://github.com/reactive/data-client/pull/3868)

### Schema.denormalize() recebe um delegate {#denormalize-delegate}

Pule esta seção se você não implementa classes [Schema](/rest/api/SchemaSimple) personalizadas.

[`Schema.denormalize()`](/rest/api/SchemaSimple) agora é `(input, delegate)` em vez da assinatura anterior de 3 parâmetros,
`(input, args, unvisit)`. O novo
[`IDenormalizeDelegate`](/rest/api/SchemaSimple) expõe `unvisit`, `args` e um novo helper `argsKey(fn)`.
[#3887](https://github.com/reactive/data-client/pull/3887)

<DiffEditor>

```ts title="Before"
import { Entity } from '@data-client/rest';

class Wrapper {
  denormalize(
    input: {},
    args: readonly any[],
    unvisit: (s: any, v: any) => any,
  ) {
    const value = unvisit(this.schema, input);
    return this.process(value, ...args);
  }
}
```

```ts title="After"
import { Entity, type IDenormalizeDelegate } from '@data-client/rest';

class Wrapper {
  denormalize(input: {}, delegate: IDenormalizeDelegate) {
    const value = delegate.unvisit(this.schema, input);
    return this.process(value, ...delegate.args);
  }
}
```

</DiffEditor>

O codemod trata métodos de classe, métodos de objeto, declarações de função, assinaturas de interface
TypeScript e chamadas de repasse `someSchema.denormalize(input, args, unvisit)`. Ele também adiciona
o import de [`IDenormalizeDelegate`](/rest/api/SchemaSimple) como um especificador `type` inline no seu import
`@data-client/*` existente (ou cria uma nova linha `import type` se nenhum for encontrado).

#### Saída dependente de args {#args-dependent-output}

Ler [`delegate.args`](/rest/api/SchemaSimple) diretamente **não** contribui para a memoização. Se a *saída* do seu schema
depende desses args (por exemplo, uma lente), declare a dependência por meio de [`delegate.argsKey(fn)`](/rest/api/SchemaSimple) para que o
cache seja separado em buckets corretamente.

<DiffEditor caption="O codemod não consegue inferir essa dependência, então atualize esses schemas manualmente.">

```ts title="Before"
class LensSchema {
  denormalize(input, args, unvisit) {
    const lens = args[0]?.portfolio;
    return this.lookup(input, lens);
  }
}
```

```ts title="After"
class LensSchema {
  constructor({ lens }) {
    // callout: The function reference is the cache key, so set it once here (or at module scope). An inline arrow would miss the cache on every call.
    this.lensSelector = lens;
  }
  denormalize(input, delegate) {
    // callout: `argsKey` returns `fn(args)` and records the dependency for memoization.
    const lens = delegate.argsKey(this.lensSelector);
    return this.lookup(input, lens);
  }
}
```

</DiffEditor>

Veja [Scalar](/rest/api/Scalar) para um exemplo completo.

### Schema.normalize() recebe um delegate {#normalize-delegate}

Pule esta seção se você não implementa classes [Schema](/rest/api/SchemaSimple) personalizadas.

[`Schema.normalize()`](/rest/api/SchemaSimple) agora lê os args do endpoint e o visitante recursivo de
[`INormalizeDelegate`](/rest/api/SchemaSimple), seguindo o formato do novo [delegate de denormalize](/rest/api/SchemaSimple).
A assinatura anterior era `(input, parent, key, args, visit, delegate, parentEntity?)`;
a nova assinatura é `(input, parent, key, delegate, parentEntity?)`.
[#3934](https://github.com/reactive/data-client/pull/3934)

<DiffEditor>

```ts title="Before"
import type { INormalizeDelegate, Visit } from '@data-client/rest';

class Wrapper {
  normalize(
    input: any,
    parent: any,
    key: string,
    args: readonly any[],
    visit: Visit,
    delegate: INormalizeDelegate,
  ) {
    const normalized = visit(this.schema, input.value, input, 'value', args);
    delegate.mergeEntity(this, this.pk(input, parent, key, args), normalized);
    return normalized;
  }
}
```

```ts title="After"
import type { INormalizeDelegate } from '@data-client/rest';

class Wrapper {
  normalize(
    input: any,
    parent: any,
    key: string,
    delegate: INormalizeDelegate,
  ) {
    const { args, visit } = delegate;
    const normalized = visit(this.schema, input.value, input, 'value');
    delegate.mergeEntity(this, this.pk(input, parent, key, args), normalized);
    return normalized;
  }
}
```

</DiffEditor>

Se o seu schema aceita o argumento opcional `parentEntity`, mantenha-o como o último argumento:

```ts
normalize(input, parent, key, delegate, parentEntity) {
  // ...
}
```

[`delegate.visit()`](/rest/api/SchemaSimple) já carrega os mesmos args para a normalização recursiva, então
[schemas](/rest/api/schema) aninhados não precisam receber os args explicitamente.

#### Aditivo: `parentEntity` em normalize {#additive-parententity-on-normalize}

O callback `visit()` do [delegate de normalize](/rest/api/SchemaSimple) rastreia internamente o schema do tipo entidade
mais próximo que o envolve e o repassa para [`Schema.normalize()`](/rest/api/SchemaSimple) como o argumento final opcional
`parentEntity`. Novos [schemas](/rest/api/schema) podem optar por descobrir a entidade que os contém
no momento da normalização (usado internamente por [Scalar](/rest/api/Scalar)).

#### Opcional: consolidar definições de Collection {#collection-consolidation}

[`Collection`](/rest/api/Collection) agora pode usar tanto [`argsKey`](/rest/api/Collection#argsKey) quanto
[`nestKey`](/rest/api/Collection#nestKey) na mesma instância. Como limpeza
opcional, substitua pares de [Collections](/rest/api/Collection) de nível superior e aninhadas por uma única definição
compartilhada:

<DiffEditor>

```ts title="Before"
export const getTodos = new RestEndpoint({
  path: '/todos',
  searchParams: {} as { userId?: string },
  schema: new Collection([Todo]),
});

class User extends Entity {
  static schema = {
    todos: new Collection([Todo], {
      nestKey: parent => ({ userId: parent.id }),
    }),
  };
}
```

```ts title="After"
export const userTodos = new Collection([Todo], {
  //argsKey: params => ({ ...params }), - this is default, so it's not needed
  nestKey: parent => ({ userId: parent.id }),
});

export const getTodos = new RestEndpoint({
  path: '/todos',
  searchParams: {} as { userId?: string },
  schema: userTodos,
});

class User extends Entity {
  static schema = {
    todos: userTodos,
  };
}
```

</DiffEditor>
