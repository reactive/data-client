## Collection.move {#collection-move}

[Collection.move](/rest/api/Collection#move) e [RestEndpoint.move](/rest/api/RestEndpoint#move) facilitam mover entidades entre collections com uma única requisição PATCH. A entidade é removida automaticamente das collections que correspondem ao seu estado antigo e adicionada às collections que correspondem aos novos valores do corpo da requisição.

Isso é útil para quadros kanban, reatribuição de grupos, mudanças de status ou qualquer fluxo em que um item se move entre listas filtradas.

```ts
const TaskResource = resource({
  path: '/tasks/:id',
  searchParams: {} as { status: string },
  schema: Task,
});

// PATCH /tasks/3 - moves task from 'backlog' to 'in-progress'
await ctrl.fetch(
  TaskResource.getList.move,
  { id: '3' },
  // highlight-next-line
  { id: '3', status: 'in-progress' },
);
```

Funciona tanto com parâmetros de caminho quanto com parâmetros de busca, e suporta collections de Array e Values.

### Collection.moveWith() {#collectionmovewith}

[Collection.moveWith()](/rest/api/Collection#moveWith) constrói um schema de mover personalizado, análogo a [addWith()](/rest/api/Collection#addWith). A função `merge` controla como as entidades são adicionadas à collection de destino (por exemplo, inserindo no início em vez de no final), enquanto o comportamento de remoção é derivado automaticamente. A função de merge [`unshift`](/rest/api/Collection#unshift-merge) é fornecida por conveniência.

```ts
import { Collection, unshift } from '@data-client/rest';

class MyCollection extends Collection {
  constructor(schema, options) {
    super(schema, options);
    // highlight-next-line
    this.move = this.moveWith(unshift);
  }
}
```

## Carregamento de dados em paralelo {#parallel-data-loading}

[useFetch()](/docs/api/useFetch) agora retorna um thenable [UsablePromise](https://react.dev/reference/react/use),
tornando `use(useFetch(endpoint, args))` um substituto direto de [useSuspense()](/docs/api/useSuspense) —
ele suspende enquanto os dados carregam, retorna os dados desnormalizados quando estão em cache, lança em caso de erro
e suspende novamente após uma [invalidação](/docs/api/Controller#invalidate).

Como `useFetch()` e `use()` são chamadas separadas, várias buscas começam em paralelo.
Todas as chamadas a `useFetch()` executam antes que qualquer `use()` suspenda, então toda busca já está em andamento
mesmo que o primeiro `use()` suspenda o componente.
Isso evita a cascata sequencial que ocorre com várias chamadas a `useSuspense()`,
em que a segunda busca não pode começar até que a primeira seja resolvida.
[#3755](https://github.com/reactive/data-client/pull/3755)

<HooksPlayground fixtures={parallelFetchFixtures} row>

```ts title="Resources" collapsed
import { Entity, resource } from '@data-client/rest';

export class Post extends Entity {
  id = 0;
  title = '';
  body = '';
  static key = 'Post';
}
export const PostResource = resource({
  path: '/posts/:id',
  schema: Post,
});

export class Comment extends Entity {
  id = 0;
  postId = 0;
  author = '';
  text = '';
  static key = 'Comment';
}
export const CommentResource = resource({
  path: '/comments/:id',
  searchParams: {} as { postId: number },
  schema: Comment,
});
```

```tsx title="PostWithComments" {7-13}
import { use } from 'react';
import { useFetch } from '@data-client/react';
import { PostResource, CommentResource } from './Resources';

function PostWithComments({ id }: { id: number }) {
  // Both fetches start in parallel
  const postPromise = useFetch(PostResource.get, { id });
  const commentsPromise = useFetch(CommentResource.getList, { postId: id });

  // use() reads the results — if the first suspends,
  // the second fetch is already in-flight
  const post = use(postPromise);
  const comments = use(commentsPromise);

  return (
    <article>
      <h3>{post.title}</h3>
      <p>{post.body}</p>
      <h4>Comments</h4>
      {comments.map(comment => (
        <div key={comment.id} className="listItem">
          <strong>{comment.author}</strong>: {comment.text}
        </div>
      ))}
    </article>
  );
}
render(<PostWithComments id={1} />);
```

## Limite de profundidade de desnormalização e Lazy {#denormalization-depth-limit--lazy}

Quando os schemas têm relações bidirecionais entre tipos de entidade
(por exemplo, `Department → Building → Department → ...`), a desnormalização percorre cada
entidade única do grafo conectado. Com conjuntos de dados pequenos isso passa despercebido, mas em escala — milhares
de entidades interconectadas — a recursão excede a pilha de chamadas do JS e lança
`RangeError: Maximum call stack size exceeded`.
[#3822](https://github.com/reactive/data-client/issues/3822)

Dois recursos complementares resolvem isso: um **limite de profundidade** como rede de segurança e
[**Lazy**](/rest/api/Lazy) para controle preciso, campo a campo, de quais relações são resolvidas de forma antecipada.

### Limite de profundidade de desnormalização {#denormalization-depth-limit}

A desnormalização agora impõe um limite de profundidade padrão de 64 saltos entre entidades. Entidades além
do limite são retornadas com ids não resolvidos em vez de objetos totalmente desnormalizados.
Um `console.error` é emitido em modo de desenvolvimento quando o limite é atingido.

O limite pode ser configurado por Entity com [`static maxEntityDepth`](/rest/api/Entity#maxEntityDepth):

```ts
class Department extends Entity {
  static maxEntityDepth = 16;
}
```

Isso evita travamentos, mas é um instrumento grosseiro — corta *todos* os caminhos profundos,
inclusive os legítimos e não cíclicos. Para um controle refinado, use [Lazy](#lazy).

### Lazy {#lazy}

[Lazy](/rest/api/Lazy) envolve um schema para pular a desnormalização antecipada de campos de relação específicos.
Durante a desnormalização da entidade pai, o campo mantém seu valor normalizado bruto (chaves primárias).
A relação pode então ser resolvida sob demanda via [useQuery](/docs/api/useQuery) usando o acessor `.query`.

```ts
import { Entity, Lazy } from '@data-client/rest';

class Department extends Entity {
  id = '';
  name = '';
  buildings: string[] = [];

  static schema = {
    // highlight-next-line
    buildings: new Lazy([Building]),
  };
}
```

Diferente do limite de profundidade, `Lazy` é uma adesão direcionada, por relação. Apenas os
campos que você marca como lazy pulam a resolução antecipada — o resto do schema é desnormalizado normalmente.
Isso também melhora o desempenho ao adiar o trabalho em relações que nem sempre são
necessárias, e oferece **isolamento de memoização** — mudanças em entidades lazy não invalidam
a forma desnormalizada do pai.

Veja a [documentação de Lazy](/rest/api/Lazy) para todos os detalhes de uso e
[#3828](https://github.com/reactive/data-client/discussions/3828) para a discussão de design.

## path-to-regexp v8 {#path-to-regexp-v8}

[RestEndpoint.path](/rest/api/RestEndpoint#path) agora usa o [path-to-regexp v8](https://github.com/pillarjs/path-to-regexp/releases/tag/v8.0.0),
que muda a sintaxe de parâmetros opcionais, parâmetros repetidos e caracteres especiais.

| Sintaxe v6 | Sintaxe v8 | Descrição |
|-----------|-----------|-------------|
| `/:optional?` | `{/:optional}` | Parâmetro opcional |
| `/:repeat+` | `/*repeat` | Repetição de um ou mais (tipado como `string[]`) |
| `/:repeat*` | `{/*repeat}` | Repetição de zero ou mais (tipado como `string[]`) |
| `/:with-dash` | `/:"with-dash"` | Nome de parâmetro entre aspas |
| `/:id(\d+)` | `/:id` | Regex personalizada removida |

### Parâmetros opcionais {#optional-parameters}

O sufixo `?` foi removido. Envolva o segmento opcional (incluindo seu prefixo) em `{}`.

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/:group/things/:number?',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '/:group/things{/:number}',
});
```

</DiffEditor>

Vários segmentos opcionais com prefixos diferentes:

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/:attr1?{-:attr2}?{-:attr3}?',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '{/:attr1}{-:attr2}{-:attr3}',
});
```

</DiffEditor>

### Parâmetros repetidos {#repeating-parameters}

Os sufixos `+` (um ou mais) e `*` (zero ou mais) foram removidos. Use a sintaxe de curinga `*name`, envolvida em `{}` para zero ou mais.

Parâmetros curinga agora são tipados como `string[]` (arrays) em vez de `string | number`, já que representam vários segmentos de caminho.

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/files/:path+',
});
ep({ path: 'docs/reports/q4' });
const optEp = new RestEndpoint({
  path: '/files/:path*',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '/files/*path',
});
ep({ path: ['docs', 'reports', 'q4'] });
const optEp = new RestEndpoint({
  path: '/files{/*path}',
});
```

</DiffEditor>

### Nomes de parâmetros entre aspas {#quoted-parameter-names}

Nomes de parâmetros com caracteres especiais (hifens, pontos) agora precisam estar entre aspas duplas:

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/:with-dash',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '/:"with-dash"',
});
```

</DiffEditor>

### Regex personalizada removida {#custom-regex-removed}

Padrões de regex inline como `/:id(\d+)` não são mais suportados. Remova a regex — valide no servidor em vez disso.

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/users/:id(\\d+)',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '/users/:id',
});
```

</DiffEditor>

### Escapando caracteres especiais {#escaping-special-characters}

Caracteres como `{}()[]+?!:*\\` precisam ser escapados com `\\` quando usados como **literais** no padrão de caminho.
Esses caracteres são [reservados pelo path-to-regexp](https://github.com/pillarjs/path-to-regexp#express--4x) e
seu uso sem escape lança um [erro Unexpected token](https://github.com/pillarjs/path-to-regexp#unexpected--or-).
Uma query string literal no padrão ainda precisa de um `?` escapado, por exemplo `'/resource\\?per_page=50'`.

Quando os segmentos de query usam **parâmetros nomeados**, prefira grupos explícitos em vez de um único `?` escapado:

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/search\\?q=:q',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '/search?{q=:q}{&page=:page}',
});
```

</DiffEditor>

### Encontrando caminhos para migrar {#finding-paths-to-migrate}

Procure estes padrões nos valores de `path:` do seu código:

- **`?`** depois de um `:param` — parâmetros opcionais a converter
- **`+`** ou **`*`** depois de um `:param` — parâmetros repetidos a converter
- **`(\`** depois de um `:param` — regex personalizada a remover
- Nomes de parâmetros com **`-`** ou **`.`** — precisam de aspas

Veja [RestEndpoint.path](/rest/api/RestEndpoint#path) para a documentação completa da sintaxe v8,
ou os [erros do path-to-regexp](https://github.com/pillarjs/path-to-regexp#errors) para explicações detalhadas.

## useFetch() retorna UsablePromise {#usefetch-returns-usablepromise}

[useFetch()](/docs/api/useFetch) agora retorna um thenable `UsablePromise` com dados desnormalizados, tratamento de erros e uma propriedade `.resolved`. Isso o torna diretamente compatível com [React.use()](https://react.dev/reference/react/use) — `use(useFetch(endpoint, args))` se comporta de forma idêntica a [useSuspense()](/docs/api/useSuspense).

Antes, `useFetch()` retornava `undefined` quando os dados eram válidos. Código que verificava se houve uma busca pela truthiness agora precisa usar `.resolved`:

<DiffEditor>

```tsx title="Before"
const promise = useFetch(PostResource.get, { id });
if (promise) {
  // fetch was triggered
}
```

```tsx title="After"
const promise = useFetch(PostResource.get, { id });
if (!promise.resolved) {
  // fetch is in-flight
}
use(promise); // suspends or returns denormalized data
```

</DiffEditor>

Veja [Carregamento de dados em paralelo](#parallel-data-loading) acima para saber como isso habilita buscas concorrentes que evitam cascatas sequenciais.
[#3752](https://github.com/reactive/data-client/pull/3752), [#3755](https://github.com/reactive/data-client/pull/3755)

## Imports diretos de schema {#direct-schema-imports}

As classes de schema agora podem ser importadas diretamente de [@data-client/endpoint](https://www.npmjs.com/package/@data-client/endpoint) (ou de [@data-client/rest](https://www.npmjs.com/package/@data-client/rest), que as reexporta), sem exigir o namespace `schema`. Isso oferece uma sintaxe de import mais limpa, mantendo total compatibilidade retroativa.

<DiffEditor>

```ts title="Before"
import { schema } from '@data-client/endpoint';

const myUnion = new schema.Union(
  { users: User, groups: Group },
  'type',
);
```

```ts title="After"
import { Union } from '@data-client/endpoint';

const myUnion = new Union(
  { users: User, groups: Group },
  'type',
);
```

</DiffEditor>

Todas as classes de schema estão disponíveis como exports diretos: [Union](/rest/api/Union), [Invalidate](/rest/api/Invalidate), [Collection](/rest/api/Collection), [Query](/rest/api/Query), [Values](/rest/api/Values), [All](/rest/api/All) e [Lazy](/rest/api/Lazy). O export do namespace `schema` continua disponível por compatibilidade retroativa.
