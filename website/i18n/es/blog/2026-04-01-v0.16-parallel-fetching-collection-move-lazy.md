## Collection.move {#collection-move}

[Collection.move](/rest/api/Collection#move) y [RestEndpoint.move](/rest/api/RestEndpoint#move) facilitan mover entidades entre collections con una sola solicitud PATCH. La entidad se elimina automáticamente de las collections que coinciden con su estado anterior y se agrega a las collections que coinciden con los nuevos valores del cuerpo de la solicitud.

Esto es útil para tableros kanban, reasignación de grupos, cambios de estado o cualquier flujo de trabajo en el que un elemento se mueva entre listas filtradas.

```ts
const TaskResource = resource({
  path: '/tasks/:id',
  searchParams: {} as { status: string },
  schema: Task,
});

// PATCH /tasks/3 - moves task from 'backlog' to 'in-progress'
await ctrl.fetch(
  TaskResource.getList.move,
  { id: '3' },
  // highlight-next-line
  { id: '3', status: 'in-progress' },
);
```

Funciona tanto con parámetros de ruta como con parámetros de búsqueda, y admite collections de tipo Array y Values.

### Collection.moveWith() {#collectionmovewith}

[Collection.moveWith()](/rest/api/Collection#moveWith) construye un schema de movimiento personalizado, análogo a [addWith()](/rest/api/Collection#addWith). La función `merge` controla cómo se agregan las entidades a su collection de destino (p. ej., insertando al inicio en lugar de al final), mientras que el comportamiento de eliminación se deriva automáticamente. Por comodidad se incluye la función de merge [`unshift`](/rest/api/Collection#unshift-merge).

```ts
import { Collection, unshift } from '@data-client/rest';

class MyCollection extends Collection {
  constructor(schema, options) {
    super(schema, options);
    // highlight-next-line
    this.move = this.moveWith(unshift);
  }
}
```

## Carga de datos en paralelo {#parallel-data-loading}

[useFetch()](/docs/api/useFetch) ahora devuelve un thenable [UsablePromise](https://react.dev/reference/react/use),
lo que convierte a `use(useFetch(endpoint, args))` en un equivalente directo de [useSuspense()](/docs/api/useSuspense):
suspende mientras se cargan los datos, devuelve los datos desnormalizados cuando están en caché, lanza en caso de error
y vuelve a suspender tras una [invalidación](/docs/api/Controller#invalidate).

Como `useFetch()` y `use()` son llamadas separadas, varias obtenciones se inician en paralelo.
Todas las llamadas a `useFetch()` se ejecutan antes de que cualquier `use()` suspenda, así que cada obtención ya está en curso
incluso si el primer `use()` suspende el componente.
Esto evita la cascada secuencial que ocurre con varias llamadas a `useSuspense()`,
donde la segunda obtención no puede comenzar hasta que se resuelve la primera.
[#3755](https://github.com/reactive/data-client/pull/3755)

<HooksPlayground fixtures={parallelFetchFixtures} row>

```ts title="Resources" collapsed
import { Entity, resource } from '@data-client/rest';

export class Post extends Entity {
  id = 0;
  title = '';
  body = '';
  static key = 'Post';
}
export const PostResource = resource({
  path: '/posts/:id',
  schema: Post,
});

export class Comment extends Entity {
  id = 0;
  postId = 0;
  author = '';
  text = '';
  static key = 'Comment';
}
export const CommentResource = resource({
  path: '/comments/:id',
  searchParams: {} as { postId: number },
  schema: Comment,
});
```

```tsx title="PostWithComments" {7-13}
import { use } from 'react';
import { useFetch } from '@data-client/react';
import { PostResource, CommentResource } from './Resources';

function PostWithComments({ id }: { id: number }) {
  // Both fetches start in parallel
  const postPromise = useFetch(PostResource.get, { id });
  const commentsPromise = useFetch(CommentResource.getList, { postId: id });

  // use() reads the results — if the first suspends,
  // the second fetch is already in-flight
  const post = use(postPromise);
  const comments = use(commentsPromise);

  return (
    <article>
      <h3>{post.title}</h3>
      <p>{post.body}</p>
      <h4>Comments</h4>
      {comments.map(comment => (
        <div key={comment.id} className="listItem">
          <strong>{comment.author}</strong>: {comment.text}
        </div>
      ))}
    </article>
  );
}
render(<PostWithComments id={1} />);
```

## Límite de profundidad de desnormalización y Lazy {#denormalization-depth-limit--lazy}

Cuando los schemas tienen relaciones bidireccionales entre tipos de entidad
(p. ej., `Department → Building → Department → ...`), la desnormalización recorre cada
entidad única del grafo conectado. Con conjuntos de datos pequeños esto pasa desapercibido, pero a gran escala (miles
de entidades interconectadas) la recursión excede la pila de llamadas de JS y lanza
`RangeError: Maximum call stack size exceeded`.
[#3822](https://github.com/reactive/data-client/issues/3822)

Dos funcionalidades complementarias abordan este problema: un **límite de profundidad** como red de seguridad, y
[**Lazy**](/rest/api/Lazy) para un control preciso, campo por campo, de qué relaciones se resuelven de forma anticipada.

### Límite de profundidad de desnormalización {#denormalization-depth-limit}

La desnormalización ahora aplica un límite de profundidad predeterminado de 64 saltos entre entidades. Las entidades más allá
del límite se devuelven con sus ids sin resolver en lugar de objetos completamente desnormalizados.
Se emite un `console.error` en modo de desarrollo cuando se alcanza el límite.

El límite puede configurarse por Entity con [`static maxEntityDepth`](/rest/api/Entity#maxEntityDepth):

```ts
class Department extends Entity {
  static maxEntityDepth = 16;
}
```

Esto evita los fallos, pero es una herramienta poco precisa: corta *todas* las rutas profundas,
incluidas las legítimas que no son cíclicas. Para un control más fino, usa [Lazy](#lazy).

### Lazy {#lazy}

[Lazy](/rest/api/Lazy) envuelve un schema para omitir la desnormalización anticipada de campos de relación específicos.
Durante la desnormalización de la entidad padre, el campo conserva su valor normalizado sin procesar (las claves primarias).
La relación puede resolverse después bajo demanda mediante [useQuery](/docs/api/useQuery) usando el accesor `.query`.

```ts
import { Entity, Lazy } from '@data-client/rest';

class Department extends Entity {
  id = '';
  name = '';
  buildings: string[] = [];

  static schema = {
    // highlight-next-line
    buildings: new Lazy([Building]),
  };
}
```

A diferencia del límite de profundidad, `Lazy` es una opción selectiva por relación. Solo los
campos que marques como lazy omiten la resolución anticipada; el resto del schema se desnormaliza con normalidad.
Esto también mejora el rendimiento al diferir el trabajo de las relaciones que no siempre se
necesitan, y proporciona **aislamiento de la memoización**: los cambios en las entidades lazy no invalidan
la forma desnormalizada del padre.

Consulta la [documentación de Lazy](/rest/api/Lazy) para ver todos los detalles de uso y
[#3828](https://github.com/reactive/data-client/discussions/3828) para la discusión de diseño.

## path-to-regexp v8 {#path-to-regexp-v8}

[RestEndpoint.path](/rest/api/RestEndpoint#path) ahora usa [path-to-regexp v8](https://github.com/pillarjs/path-to-regexp/releases/tag/v8.0.0),
que cambia la sintaxis de los parámetros opcionales, los parámetros repetidos y los caracteres especiales.

| Sintaxis v6 | Sintaxis v8 | Descripción |
|-----------|-----------|-------------|
| `/:optional?` | `{/:optional}` | Parámetro opcional |
| `/:repeat+` | `/*repeat` | Repetición de uno o más (tipado como `string[]`) |
| `/:repeat*` | `{/*repeat}` | Repetición de cero o más (tipado como `string[]`) |
| `/:with-dash` | `/:"with-dash"` | Nombre de parámetro entre comillas |
| `/:id(\d+)` | `/:id` | Se eliminan las expresiones regulares personalizadas |

### Parámetros opcionales {#optional-parameters}

Se elimina el sufijo `?`. Envuelve el segmento opcional (incluido su prefijo) en `{}`.

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/:group/things/:number?',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '/:group/things{/:number}',
});
```

</DiffEditor>

Varios segmentos opcionales con prefijos distintos:

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/:attr1?{-:attr2}?{-:attr3}?',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '{/:attr1}{-:attr2}{-:attr3}',
});
```

</DiffEditor>

### Parámetros repetidos {#repeating-parameters}

Se eliminan los sufijos `+` (uno o más) y `*` (cero o más). Usa la sintaxis de comodín `*name`, envuelta en `{}` para cero o más.

Los parámetros comodín ahora se tipan como `string[]` (arreglos) en lugar de `string | number`, ya que representan varios segmentos de la ruta.

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/files/:path+',
});
ep({ path: 'docs/reports/q4' });
const optEp = new RestEndpoint({
  path: '/files/:path*',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '/files/*path',
});
ep({ path: ['docs', 'reports', 'q4'] });
const optEp = new RestEndpoint({
  path: '/files{/*path}',
});
```

</DiffEditor>

### Nombres de parámetros entre comillas {#quoted-parameter-names}

Los nombres de parámetros con caracteres especiales (guiones, puntos) ahora deben ir entre comillas dobles:

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/:with-dash',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '/:"with-dash"',
});
```

</DiffEditor>

### Se eliminan las expresiones regulares personalizadas {#custom-regex-removed}

Los patrones de expresiones regulares inline como `/:id(\d+)` ya no se admiten. Elimina la expresión regular y valida en el servidor en su lugar.

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/users/:id(\\d+)',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '/users/:id',
});
```

</DiffEditor>

### Escapar caracteres especiales {#escaping-special-characters}

Los caracteres como `{}()[]+?!:*\\` deben escaparse con `\\` cuando se usan como **literales** en el patrón de la ruta.
Estos caracteres están [reservados por path-to-regexp](https://github.com/pillarjs/path-to-regexp#express--4x) y
usarlos sin escapar lanza un [error Unexpected token](https://github.com/pillarjs/path-to-regexp#unexpected--or-).
Una cadena de consulta literal en el patrón sigue necesitando un `?` escapado, p. ej. `'/resource\\?per_page=50'`.

Cuando los segmentos de consulta usan **parámetros con nombre**, prefiere grupos explícitos en lugar de un único `?` escapado:

<DiffEditor>

```ts title="Before"
const ep = new RestEndpoint({
  path: '/search\\?q=:q',
});
```

```ts title="After"
const ep = new RestEndpoint({
  path: '/search?{q=:q}{&page=:page}',
});
```

</DiffEditor>

### Encontrar las rutas que hay que migrar {#finding-paths-to-migrate}

Busca en tu base de código estos patrones en los valores de `path:`:

- **`?`** después de un `:param`: parámetros opcionales que hay que convertir
- **`+`** o **`*`** después de un `:param`: parámetros repetidos que hay que convertir
- **`(\`** después de un `:param`: expresiones regulares personalizadas que hay que eliminar
- Nombres de parámetros con **`-`** o **`.`**: necesitan comillas

Consulta [RestEndpoint.path](/rest/api/RestEndpoint#path) para la documentación completa de la sintaxis v8,
o los [errores de path-to-regexp](https://github.com/pillarjs/path-to-regexp#errors) para explicaciones detalladas.

## useFetch() devuelve UsablePromise {#usefetch-returns-usablepromise}

[useFetch()](/docs/api/useFetch) ahora devuelve un thenable `UsablePromise` con datos desnormalizados, manejo de errores y una propiedad `.resolved`. Esto lo hace directamente compatible con [React.use()](https://react.dev/reference/react/use): `use(useFetch(endpoint, args))` se comporta exactamente igual que [useSuspense()](/docs/api/useSuspense).

Antes, `useFetch()` devolvía `undefined` cuando los datos eran válidos. El código que comprobaba si hubo una obtención mediante su veracidad ahora debe usar `.resolved`:

<DiffEditor>

```tsx title="Before"
const promise = useFetch(PostResource.get, { id });
if (promise) {
  // fetch was triggered
}
```

```tsx title="After"
const promise = useFetch(PostResource.get, { id });
if (!promise.resolved) {
  // fetch is in-flight
}
use(promise); // suspends or returns denormalized data
```

</DiffEditor>

Consulta [Carga de datos en paralelo](#parallel-data-loading) más arriba para ver cómo esto permite obtenciones concurrentes que evitan las cascadas secuenciales.
[#3752](https://github.com/reactive/data-client/pull/3752), [#3755](https://github.com/reactive/data-client/pull/3755)

## Importaciones directas de schemas {#direct-schema-imports}

Las clases de schema ahora pueden importarse directamente desde [@data-client/endpoint](https://www.npmjs.com/package/@data-client/endpoint) (o desde [@data-client/rest](https://www.npmjs.com/package/@data-client/rest), que las reexporta) en lugar de requerir el espacio de nombres `schema`. Esto ofrece una sintaxis de importación más limpia manteniendo la compatibilidad hacia atrás completa.

<DiffEditor>

```ts title="Before"
import { schema } from '@data-client/endpoint';

const myUnion = new schema.Union(
  { users: User, groups: Group },
  'type',
);
```

```ts title="After"
import { Union } from '@data-client/endpoint';

const myUnion = new Union(
  { users: User, groups: Group },
  'type',
);
```

</DiffEditor>

Todas las clases de schema están disponibles como exportaciones directas: [Union](/rest/api/Union), [Invalidate](/rest/api/Invalidate), [Collection](/rest/api/Collection), [Query](/rest/api/Query), [Values](/rest/api/Values), [All](/rest/api/All) y [Lazy](/rest/api/Lazy). La exportación del espacio de nombres `schema` sigue disponible por compatibilidad hacia atrás.
