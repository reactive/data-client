v0.18 se centra en un modelado de datos más rico para valores que varían según el contexto de la petición, descargas tipadas más simples y una coincidencia de collections que refleja mejor los filtros reales de las APIs.

**Nuevas funcionalidades:**

- [Schema Scalar](/blog/2026/05/01/v0.18-scalar-typed-downloads#scalar) - Campos de entidad dependientes de un lens (p. ej. valores específicos de un portafolio) sin mutar jamás la entidad subyacente
- [Propiedad `content` de RestEndpoint](/blog/2026/05/01/v0.18-scalar-typed-downloads#content-property) - Descargas de archivos tipadas, respuestas de texto y streaming con una sola propiedad
- [`nonFilterArgumentKeys` en resource()](/blog/2026/05/01/v0.18-scalar-typed-downloads#non-filter-argument-keys) - Los argumentos de ordenamiento/paginación no fragmentan tus [Collections](/rest/api/Collection)

**Otras mejoras:**

- [Detección automática de Content-Type binarios](/blog/2026/05/01/v0.18-scalar-typed-downloads#binary-auto-detection) - Las imágenes, PDFs y otras respuestas binarias se manejan automáticamente sin configuración ([#3868](https://github.com/reactive/data-client/pull/3868))
- [Los tipos de body de los extenders de Collection coinciden con la semántica del método HTTP](/rest/api/Collection) - Los extenders PATCH (`.move`, `.remove`) aceptan bodies parciales; un [RestEndpoint](/rest/api/RestEndpoint) independiente deriva un body tipado a partir del schema de entidad de la [Collection](/rest/api/Collection) ([#3910](https://github.com/reactive/data-client/pull/3910))
- Se exporta [`CollectionOptions`](/rest/api/Collection) desde `@data-client/endpoint` y `@data-client/rest` para construir [Collections](/rest/api/Collection) con tipado ([#3904](https://github.com/reactive/data-client/pull/3904))

## Scalar {#scalar}

[Scalar](/rest/api/Scalar) maneja campos de [Entity](/rest/api/Entity) cuyos valores dependen de un "lens" en tiempo de ejecución, como el
portafolio, la moneda o la configuración regional seleccionados. Varios componentes pueden renderizar la **misma** entidad a través de
distintos lenses simultáneamente, cada uno viendo los valores correctos, mientras la entidad en sí nunca
cambia. Los valores dependientes del lens viven en una tabla de celdas separada y se unen al momento de desnormalizar
a partir de los argumentos del endpoint.

Las referencias a `name` y `price` permanecen estables al cambiar de portafolio porque la entidad `Company`
en sí nunca cambia; solo lo hace la celda [`Scalar`](/rest/api/Scalar) seleccionada por el lens actual. Una sola instancia de [`Scalar`](/rest/api/Scalar)
puede servir tanto como campo de [`Entity.schema`](/rest/api/Entity#schema) (la entidad padre se infiere de la visita) como
de forma independiente dentro de [`Values`](/rest/api/Values), [`[Scalar]`](/rest/api/Array)
o [`Collection([Scalar])`](/rest/api/Collection) para refrescos baratos de solo columnas (la entidad se vincula
explícitamente mediante [`entity`](/rest/api/Scalar#entity)). Las pks de las celdas se derivan de la clave del mapa o mediante
[`Scalar.entityPk()`](/rest/api/Scalar#entityPk), que por defecto usa [`Entity.pk()`](/rest/api/Entity#pk), de modo que las claves primarias personalizadas y
compuestas funcionan sin necesidad de sobrescribir nada.

El store normalizado mantiene la entidad estable y las celdas del lens separadas:

```
entities['Company']['1'] = {
  id: '1',
  price: 145.20,
  pct_equity: ['1', 'pct_equity', 'Company'],
  shares: ['1', 'shares', 'Company'],
}

entities['Scalar(portfolio)']['Company|1|A'] = { pct_equity: 0.50, shares: 10000 }
entities['Scalar(portfolio)']['Company|1|B'] = { pct_equity: 0.30, shares: 6000 }
```

La demo combina `getCompanies` con un refresco barato de solo lens, `getPortfolioColumns`, que escribe
en la misma tabla de celdas; consulta la [documentación de Scalar](/rest/api/Scalar) para un recorrido completo
del comportamiento de la caché.

[`Scalar`](/rest/api/Scalar) también implementa [queryKey](/rest/api/Scalar#queryKey), por lo que participa directamente en
[useQuery](/docs/api/useQuery), [Controller.get](/docs/api/Controller#get) y [schema.Query](/rest/api/Query),
toda la superficie [Queryable](/rest/api/schema#queryable), enumerando sus celdas para el lens actual.

[#3887](https://github.com/reactive/data-client/pull/3887) - [Documentación de Scalar](/rest/api/Scalar)

## Propiedad `content` de RestEndpoint {#content-property}

[RestEndpoint](/rest/api/RestEndpoint) ahora acepta una propiedad [`content`](/rest/api/RestEndpoint#content) que controla
cómo se analiza el cuerpo de la respuesta. El tipo de retorno se infiere automáticamente a partir del valor, y `schema` queda
restringido a `undefined` a nivel de tipos para los tipos de contenido que no son JSON.

```typescript
import { RestEndpoint } from '@data-client/rest';

const downloadFile = new RestEndpoint({
  path: '/files/:id/download',
  // highlight-next-line
  content: 'blob',
  dataExpiryLength: 0,
});

// Return type is Blob — inferred from content, no explicit generics needed
const blob: Blob = await ctrl.fetch(downloadFile, { id: '123' });
```

Antes, las descargas de archivos requerían una sobrescritura verbosa de `parseResponse`. Ahora es una sola propiedad.

| Valor | Se analiza mediante | Tipo de retorno |
|---|---|---|
| `'json'` | `response.json()` | `any` |
| `'blob'` | `response.blob()` | `Blob` |
| `'text'` | `response.text()` | `string` |
| `'arrayBuffer'` | `response.arrayBuffer()` | `ArrayBuffer` |
| `'stream'` | `response.body` | `ReadableStream<Uint8Array>` |

Establecer `content` en un valor que no sea JSON obliga a `schema: undefined` a nivel de tipos, ya que los datos binarios no pueden
normalizarse. Una comprobación en tiempo de ejecución ofrece un mensaje de error claro si se usa por accidente un schema normalizable.

Funciona con [`extend()`](/rest/api/RestEndpoint#extend) y con [subclases](/rest/api/RestEndpoint#inheritance):

```typescript
// Extend a JSON endpoint into a blob downloader
const download = jsonEndpoint.extend({
  content: 'blob',
  schema: undefined,
});

// Subclass for a reusable blob endpoint type
class BlobEndpoint<O extends RestGenerics = any> extends RestEndpoint<O> {
  content = 'blob' as const;
}
```

[#3868](https://github.com/reactive/data-client/pull/3868) - [Documentación de `content`](/rest/api/RestEndpoint#content)

## `nonFilterArgumentKeys` en resource() {#non-filter-argument-keys}

[`nonFilterArgumentKeys`](/rest/api/Collection#nonFilterArgumentKeys) permite a [resource()](/rest/api/resource)
declarar qué claves de argumentos *no* se usan para filtrar los resultados de la collection; normalmente opciones de ordenamiento,
paginación o visualización. Sin ella, cada combinación distinta de argumentos de ordenamiento o página crearía un bucket separado de
[Collection](/rest/api/Collection), y los elementos recién creados no aparecerían en las listas con
argumentos de ordenamiento distintos aunque los datos subyacentes deberían coincidir.

```ts
import { Entity, resource } from '@data-client/rest';

class Post extends Entity {
  id = '';
  title = '';
  group = '';
  author = '';
}

const PostResource = resource({
  path: '/:group/posts/:id',
  searchParams: {} as { orderBy?: string; author?: string },
  schema: Post,
  // highlight-next-line
  nonFilterArgumentKeys: ['orderBy'],
});
```

Ahora `group` y `author` son claves de filtro (separan las [Collections](/rest/api/Collection) en buckets), pero `orderBy` se
comparte: `PostResource.getList.push()` agrega el nuevo post a *todas* las variantes de `orderBy` de un bucket
`{ group, author }` dado.

Acepta un `string[]`, una `RegExp` o una función predicado:

```ts
nonFilterArgumentKeys: /^(orderBy|page|cursor)$/,
```

[#3914](https://github.com/reactive/data-client/pull/3914) - [Documentación de `nonFilterArgumentKeys`](/rest/api/Collection#nonFilterArgumentKeys)

## Detección automática de Content-Type binarios {#binary-auto-detection}

Cuando `content` no está establecido, [`parseResponse`](/rest/api/RestEndpoint#parseResponse) ahora detecta automáticamente los
Content-Type binarios y devuelve `response.blob()` en lugar de corromper los datos mediante `.text()`.

Los tipos binarios como `image/*`, `audio/*`, `video/*`, `font/*`, `application/octet-stream`, `application/pdf` y
otros ahora se manejan automáticamente. Los tipos de texto (`text/*`, XML, HTML, JavaScript, CSS, etc.) siguen
usando el respaldo de texto existente con mensajes de error que tienen en cuenta el schema.

Esto significa que los endpoints que sirven datos binarios con cabeceras Content-Type correctas funcionan sin ninguna configuración:

```typescript
const ep = new RestEndpoint({
  path: '/avatars/:id',
});
// Server responds with Content-Type: image/png
// → automatically returns a Blob (previously corrupted via .text())
```

[#3868](https://github.com/reactive/data-client/pull/3868)

### Schema.denormalize() recibe un delegate {#denormalize-delegate}

Omite esta sección si no implementas clases [Schema](/rest/api/SchemaSimple) personalizadas.

[`Schema.denormalize()`](/rest/api/SchemaSimple) ahora es `(input, delegate)` en lugar de la firma anterior de 3 parámetros
`(input, args, unvisit)`. El nuevo
[`IDenormalizeDelegate`](/rest/api/SchemaSimple) expone `unvisit`, `args` y un nuevo helper `argsKey(fn)`.
[#3887](https://github.com/reactive/data-client/pull/3887)

<DiffEditor>

```ts title="Before"
import { Entity } from '@data-client/rest';

class Wrapper {
  denormalize(
    input: {},
    args: readonly any[],
    unvisit: (s: any, v: any) => any,
  ) {
    const value = unvisit(this.schema, input);
    return this.process(value, ...args);
  }
}
```

```ts title="After"
import { Entity, type IDenormalizeDelegate } from '@data-client/rest';

class Wrapper {
  denormalize(input: {}, delegate: IDenormalizeDelegate) {
    const value = delegate.unvisit(this.schema, input);
    return this.process(value, ...delegate.args);
  }
}
```

</DiffEditor>

El codemod maneja métodos de clase, métodos de objeto, declaraciones de función, firmas de interfaces de
TypeScript y llamadas de paso directo `someSchema.denormalize(input, args, unvisit)`. También agrega
la importación de [`IDenormalizeDelegate`](/rest/api/SchemaSimple) como especificador `type` en línea en tu importación existente de
`@data-client/*` (o crea una nueva línea `import type` si no encuentra ninguna).

#### Salida dependiente de los argumentos {#args-dependent-output}

Leer [`delegate.args`](/rest/api/SchemaSimple) directamente **no** contribuye a la memoización. Si la *salida* de tu schema
depende de esos argumentos (p. ej. un lens), declara la dependencia mediante [`delegate.argsKey(fn)`](/rest/api/SchemaSimple) para que la
caché se divida en buckets correctamente.

<DiffEditor caption="El codemod no puede inferir esta dependencia, así que actualiza estos schemas a mano.">

```ts title="Before"
class LensSchema {
  denormalize(input, args, unvisit) {
    const lens = args[0]?.portfolio;
    return this.lookup(input, lens);
  }
}
```

```ts title="After"
class LensSchema {
  constructor({ lens }) {
    // callout: The function reference is the cache key, so set it once here (or at module scope). An inline arrow would miss the cache on every call.
    this.lensSelector = lens;
  }
  denormalize(input, delegate) {
    // callout: `argsKey` returns `fn(args)` and records the dependency for memoization.
    const lens = delegate.argsKey(this.lensSelector);
    return this.lookup(input, lens);
  }
}
```

</DiffEditor>

Consulta [Scalar](/rest/api/Scalar) para ver un ejemplo desarrollado.

### Schema.normalize() recibe un delegate {#normalize-delegate}

Omite esta sección si no implementas clases [Schema](/rest/api/SchemaSimple) personalizadas.

[`Schema.normalize()`](/rest/api/SchemaSimple) ahora lee los argumentos del endpoint y el visitante recursivo desde
[`INormalizeDelegate`](/rest/api/SchemaSimple), en línea con la nueva forma del [delegate de denormalize](/rest/api/SchemaSimple).
La firma anterior era `(input, parent, key, args, visit, delegate, parentEntity?)`;
la nueva firma es `(input, parent, key, delegate, parentEntity?)`.
[#3934](https://github.com/reactive/data-client/pull/3934)

<DiffEditor>

```ts title="Before"
import type { INormalizeDelegate, Visit } from '@data-client/rest';

class Wrapper {
  normalize(
    input: any,
    parent: any,
    key: string,
    args: readonly any[],
    visit: Visit,
    delegate: INormalizeDelegate,
  ) {
    const normalized = visit(this.schema, input.value, input, 'value', args);
    delegate.mergeEntity(this, this.pk(input, parent, key, args), normalized);
    return normalized;
  }
}
```

```ts title="After"
import type { INormalizeDelegate } from '@data-client/rest';

class Wrapper {
  normalize(
    input: any,
    parent: any,
    key: string,
    delegate: INormalizeDelegate,
  ) {
    const { args, visit } = delegate;
    const normalized = visit(this.schema, input.value, input, 'value');
    delegate.mergeEntity(this, this.pk(input, parent, key, args), normalized);
    return normalized;
  }
}
```

</DiffEditor>

Si tu schema acepta el argumento opcional `parentEntity`, mantenlo como el último argumento:

```ts
normalize(input, parent, key, delegate, parentEntity) {
  // ...
}
```

[`delegate.visit()`](/rest/api/SchemaSimple) ya lleva los mismos argumentos para la normalización recursiva, por lo que los
[schemas](/rest/api/schema) anidados no necesitan recibir los argumentos explícitamente.

#### Aditivo: `parentEntity` en normalize {#additive-parententity-on-normalize}

El callback `visit()` del [delegate de normalize](/rest/api/SchemaSimple) rastrea internamente el schema de tipo entidad
más cercano que lo contiene y lo reenvía a [`Schema.normalize()`](/rest/api/SchemaSimple) como el argumento final opcional
`parentEntity`. Los nuevos [schemas](/rest/api/schema) pueden optar por descubrir la entidad que los contiene
al momento de normalizar (usado internamente por [Scalar](/rest/api/Scalar)).

#### Opcional: consolidar las definiciones de Collection {#collection-consolidation}

[`Collection`](/rest/api/Collection) ahora puede usar tanto [`argsKey`](/rest/api/Collection#argsKey) como
[`nestKey`](/rest/api/Collection#nestKey) en la misma instancia. Como limpieza
opcional, reemplaza los pares de [Collections](/rest/api/Collection) de nivel superior y anidadas por una sola
definición compartida:

<DiffEditor>

```ts title="Before"
export const getTodos = new RestEndpoint({
  path: '/todos',
  searchParams: {} as { userId?: string },
  schema: new Collection([Todo]),
});

class User extends Entity {
  static schema = {
    todos: new Collection([Todo], {
      nestKey: parent => ({ userId: parent.id }),
    }),
  };
}
```

```ts title="After"
export const userTodos = new Collection([Todo], {
  //argsKey: params => ({ ...params }), - this is default, so it's not needed
  nestKey: parent => ({ userId: parent.id }),
});

export const getTodos = new RestEndpoint({
  path: '/todos',
  searchParams: {} as { userId?: string },
  schema: userTodos,
});

class User extends Entity {
  static schema = {
    todos: userTodos,
  };
}
```

</DiffEditor>
