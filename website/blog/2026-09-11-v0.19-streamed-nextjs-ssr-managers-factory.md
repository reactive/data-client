v0.19 hydrates SSR store state incrementally — a baseline in the shell, then a delta per committed
server revision — and starts the move of `managers` to a function form.

**Platforms:**

- [Incremental streamed hydration](/blog/2026/09/11/v0.19-streamed-nextjs-ssr-managers-factory#streamed-ssr) — SSR store state arrives as a baseline plus per-flush deltas. Each island hydrates from the folded snapshot when its piece is already present. Live `HYDRATE` runs from the receiver layout effect; RSC may start a Client Component first, and a miss then fetches like any client render. Next.js App Router is the first adapter ([#4090](https://github.com/reactive/data-client/pull/4090))
- [`managers` as a function](/blog/2026/09/11/v0.19-streamed-nextjs-ssr-managers-factory#managers-factory) - `managers={() => [...]}` on [DataProvider](/docs/api/DataProvider#managers); the long-term form
- [Hydration reads the server snapshot](/blog/2026/09/11/v0.19-streamed-nextjs-ssr-managers-factory#hydration-snapshot) - A `Suspense` boundary that hydrates after a Manager or mutation updated the store no longer produces a hydration mismatch

**New APIs:**

- [`HYDRATE` action](/docs/api/Actions#hydrate) - Merges streamed server state into the client store; `StateDelta` and `StateBaseline` types

**Other Improvements:**

- Serialized SSR state is escaped, so an API response containing `</script>` can no longer break out of its tag
- `nonce` prop on the Next.js [DataProvider](/docs/guides/ssr#nonce) for Content-Security-Policy

**[Breaking Changes:](/blog/2026/09/11/v0.19-streamed-nextjs-ssr-managers-factory#migration-guide)**

- [Next.js `DataProvider` `managers` is a function](/blog/2026/09/11/v0.19-streamed-nextjs-ssr-managers-factory#nextjs-managers) - `managers={[...]}` → `managers={() => [...]}`. Affects `@data-client/react/nextjs` only.
- [`ActionTypes` includes `HydrateAction`](/blog/2026/09/11/v0.19-streamed-nextjs-ssr-managers-factory#custom-managers) - Affects custom [Managers](/docs/api/Manager) with exhaustive `switch` statements only.

## Incremental streamed hydration {#streamed-ssr}

The shell carries an inert baseline. Each later committed server revision emits a `StateDelta`.
The client folds that piece into the hydration snapshot and dispatches `HYDRATE` into the live
store from the receiver layout effect.

```tsx title="app/[userId]/page.tsx"
export default async function TodoPage({ params }) {
  const { userId } = await params; // resolves after the shell was sent
  return <TodoList userId={userId} />; // 'use client' + useSuspense
}
```

On Next.js, RSC may run a Client Component before the HTML delta and before that layout
effect. A miss then fetches like any client render. Per-key waiters that would suppress that
refetch are not in this release. The figures are in the
[SSR guide](/docs/guides/ssr#streamed-hydration). Next.js App Router is the first adapter;
generic `renderToPipeableStream` remains a one-shot document snapshot.

Nothing changes in how you write components. See the [SSR guide](/docs/guides/ssr#nextjs) for the
`nonce` prop and limitations.

## Hydration reads the server snapshot {#hydration-snapshot}

While React hydrates server-rendered HTML, hooks now read the state the server rendered with rather
than the live store. A boundary that hydrates after a polling or WebSocket [Manager](/docs/api/Manager)
already updated the store matches its HTML, then converges to the live value. Updates still flow
through React state, so transitions stay non-blocking.

## `managers` as a function {#managers-factory}

[DataProvider](/docs/api/DataProvider#managers) accepts a function that creates the managers. It is
called once when the provider mounts.

```tsx
import { DataProvider, getDefaultManagers } from '@data-client/react';

// highlight-next-line
const managers = () => [...getDefaultManagers(), new MyManager()];

<DataProvider managers={managers}>
  <App />
</DataProvider>;
```

This is the form the library is moving to. The Next.js provider builds a store per request and can
only take a function; in the browser it also gives each `DataProvider` on a page its own instances
instead of one hoisted array bound to whichever store mounted last.

:::warning Arrays are transitional

`managers={[...]}` still works on the browser `DataProvider`, but will be removed in a future
release. Migrate to `managers={() => [...]}` as soon as you can.

:::

#### For Next.js App Router users {#nextjs-managers}

Skip this section if you do not pass `managers` to the `@data-client/react/nextjs` provider.

The same change is required here: an array throws with a migration hint. The function runs once per
request on the server and once in the browser.

<DiffEditor>

```tsx title="Before"
'use client';
import { getDefaultManagers } from '@data-client/react';
import { DataProvider } from '@data-client/react/nextjs';

const managers = [...getDefaultManagers(), new MyManager()];

export default function Provider({ children }) {
  return <DataProvider managers={managers}>{children}</DataProvider>;
}
```

```tsx title="After"
'use client';
import { getDefaultManagers } from '@data-client/react';
import { DataProvider } from '@data-client/react/nextjs';

const managers = () => [...getDefaultManagers(), new MyManager()];

export default function Provider({ children }) {
  return <DataProvider managers={managers}>{children}</DataProvider>;
}
```

</DiffEditor>

### For custom Manager authors {#custom-managers}

Skip this section if you don't have custom [Managers](/docs/concepts/managers).

`ActionTypes` now includes [`HydrateAction`](/docs/api/Actions#hydrate). Middleware that narrows on
`action.type` with an exhaustive `switch` needs a `default` branch or a case for
`actionTypes.HYDRATE`; middleware that only inspects the actions it cares about is unaffected.
